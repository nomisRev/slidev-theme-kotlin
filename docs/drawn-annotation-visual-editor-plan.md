# DrawnAnnotation visual editor plan

**Status:** in progress — Phases 0–3 are implemented; Phase 4 authoring polish is underway. This is the manual-first alternative to `drawn-annotation-rewrite-plan.md`.

## 1. Product direction

Instead of building a sophisticated collision solver, make annotation geometry directly editable in Slidev's development view:

1. An annotation gets a stable authored `id`.
2. The author enters **annotation edit mode** on the current slide.
3. The author drags/resizes the label and adjusts the connector with handles.
4. The browser previews changes immediately in slide coordinates.
5. On pointer release, a development-only server endpoint writes normalized values to a generated project CSS file.
6. CSS HMR applies the saved geometry without restarting Slidev.
7. Build, export, presenter mode, and deployed decks only consume the CSS. They contain no editor UI or write capability.

This makes the author, rather than a runtime solver, responsible for the final composition. The component should still provide a reasonable initial position, but it no longer needs to infer all obstacles or predict future slide states.

## 2. Scope

### First release

- Move a label.
- Resize its maximum width.
- Edit a connector as a line with two endpoints.
- Drag either endpoint to change length and angle.
- Drag the line body to translate both endpoints.
- Reset label, connector, or the entire annotation to defaults.
- Persist normalized values in project CSS.
- Preserve current source lookup, rough marks, clicks, sequencing, Magic Move tracking, animation, accessibility, targets, arrows, and export behavior.

### Deliberately deferred

- Automatic collision avoidance.
- Orthogonal/multi-bend connector routing.
- Editing the RoughJS wobble itself.
- Different saved geometry for every click state.
- Collaborative/multi-user editing.
- Editing production builds.

## 3. Authoring contract and stable identity

Add a required-in-edit-mode `id` prop:

```html
<DrawnAnnotation
  id="nullable-return-label"
  text="String?"
  label="nullable return type"
  :on="2"
>
```

For the first release, IDs should be unique across the whole deck, not merely within a slide. That keeps generated CSS selectors stable when slides are reordered and avoids coupling saved geometry to Slidev page numbers.

- Runtime rendering remains possible without `id`; the annotation uses its default geometry but is not editable or persistable.
- Edit mode shows an actionable warning for a missing ID.
- Duplicate IDs are a development error and disable saving for those annotations.
- Restrict IDs to a documented safe form such as `[A-Za-z][A-Za-z0-9_.-]*`; this keeps diagnostics, CSS selectors, and generated output predictable.

If deck-wide uniqueness proves too inconvenient, a later version can combine a stable slide frontmatter key with a slide-local annotation ID. Do not use slide number as persisted identity because inserting a slide would retarget all later rules.

## 4. Persisted geometry

Use normalized slide coordinates, not viewport pixels. Values remain correct under presenter scaling, browser resizing, export, and a different `canvasWidth`.

A generated file could contain:

```css
/* Generated by the DrawnAnnotation editor. Do not edit while Slidev is running. */
[data-drawn-annotation-id="nullable-return-label"] {
  --da-label-x: 0.7125;
  --da-label-y: 0.1864;
  --da-label-width: 0.1944;

  --da-connector-x1: 0.5028;
  --da-connector-y1: 0.2419;
  --da-connector-x2: 0.6486;
  --da-connector-y2: 0.2012;
}
```

The numbers are fractions of the slide width/height. The component reads the custom properties with `getComputedStyle()` and converts them to its slide-local SVG coordinates. Unitless fractions are preferable to CSS percentages because the current component can be nested in positioned or transformed content; they always refer explicitly to the measured Slidev slide root rather than to an accidental CSS containing block.

Suggested file:

```text
styles/drawn-annotations.generated.css
```

The deck imports it once from its normal `style.css`:

```css
@import './styles/drawn-annotations.generated.css';
```

The generated file is committed to source control. It is wholly tool-owned and rewritten deterministically, which is safer than trying to patch arbitrary hand-written CSS. Rules are sorted by annotation ID and properties use fixed precision to avoid noisy diffs.

### Geometry precedence

Use one explicit precedence order:

1. generated CSS custom property;
2. existing manual prop (`label-x`, `label-y`, `label-width`);
3. simple runtime default.

For an unedited label, retain a bounded, simple default placement near the source. It may honor `placement`, but should not scan the entire DOM or promise collision avoidance. The first drag materializes the current position into normalized CSS values, so entering edit mode never makes the label jump.

An unedited connector continues to be derived from the source and label/target. Once connector endpoints are saved, it becomes a manually positioned connector. A toolbar action can return it to attached/automatic behavior.

## 5. Connector model

For the first release, represent manual connector geometry as two normalized endpoints:

```ts
interface ManualConnectorGeometry {
  x1: number
  y1: number
  x2: number
  y2: number
}
```

This directly supports the requested operations:

- drag endpoint 1 or 2: rotate and lengthen/shorten;
- drag the line body: move the complete connector;
- arrow rendering: keep the arrow at endpoint 2 and orient it from the final tangent;
- rough appearance: regenerate the RoughJS path from the two points with the existing stable seed.

Keep the existing `curve` prop as the default bow. A later editor handle may persist `--da-connector-curve`. Do not persist SVG path strings: they are not scalable, are hard to edit, and tie saved data to a particular RoughJS output.

Offer optional snapping while dragging:

- source mark ports/centre;
- label edge ports;
- target point;
- slide guides and other connector endpoints.

The initial implementation supplies slide edge/centre guides plus the current annotation's source ports, target point, and label edge ports; cross-annotation endpoint snapping can follow when the shared overlay registry lands. Snapping changes only the saved endpoint coordinates; it does not create a new routing system. Holding `Alt` temporarily disables snapping.

## 6. Slide-local rendering and editor architecture

Split the implementation into four small layers:

```text
DrawnAnnotation.vue
  retained source/click/animation behavior; consumes resolved geometry
        ↓
annotation geometry adapter
  reads CSS variables, resolves defaults, converts slide fractions to local points
        ↓
development editor registry/store
  active slide annotations, selection, draft geometry, duplicate-ID checks
        ↓
development writer client + Vite plugin
  validates and atomically rewrites generated CSS
```

Suggested files:

```text
components/drawn-annotation/
  geometry.ts
  persisted-geometry.ts
  editor-store.ts
  editor-overlay.vue
  writer-client.ts
components/DrawnAnnotation.vue
plugins/drawn-annotation-editor.ts
styles/drawn-annotations.generated.css
```

Use one slide-local editor overlay for selection boxes and handles. Do not place handles inside every annotation SVG: annotations can be nested in clipped/transformed components, and overlapping controls would compete for pointer events. Each annotation registers its source box, label box, connector, slide root, visibility, and callbacks with the store.

The visible label and connector should ultimately render in a shared layer owned by the concrete `.slidev-layout` root, or otherwise use explicit viewport-to-slide conversion. This guarantees that the saved fractions and editor handles share one coordinate origin even for annotations nested in components. Source marks can retain their current ownership and tracking as long as their measured boxes are converted to the same slide coordinates.

## 7. Edit-mode interaction

Add a development-only toolbar in a theme global layer:

- **Edit annotations** toggle, with a keyboard shortcut that does not conflict with Slidev;
- selected annotation ID;
- reset label / reset connector / reset all;
- attached/manual connector toggle;
- save status and errors.

Behavior:

1. Edit mode is available only in normal slide view (optionally presenter view later), never overview, preview-next, print, or export.
2. Only annotations visible at the current click are selectable.
3. Clicking a label or connector selects it without advancing the slide.
4. Label drag updates an in-memory draft on every pointer move.
5. A width handle changes the normalized maximum width; height remains content-driven.
6. Connector endpoint/body drags update the draft similarly.
7. Saving occurs on pointer release and is also debounced after a pause in a long drag, not on every pointer move. Browser-side writes are serialized so an automatic save and a release save use successive revisions rather than conflicting with one another.
8. `Escape` cancels the active drag; undo restores the prior persisted snapshot.
9. Entering/leaving edit mode does not change click count or replay drawing animations.

During a drag, apply draft geometry directly from Vue state. Do not wait for CSS HMR. After the server confirms the write and the stylesheet updates, clear the draft only when the persisted revision matches it, avoiding a one-frame snap back.

Slidev's built-in `v-drag` is useful interaction precedent but is not the right persistence model here: it writes element rectangles to Markdown/frontmatter in slide pixels and does not model annotation connectors. Reuse its ideas—slide scale conversion, active selection, keyboard movement, click-outside handling—but keep annotation geometry and CSS persistence independent.

## 8. Development-only persistence bridge

Browser code cannot safely write a project file by itself. Export a small Vite plugin from the theme package and ask consuming decks to enable it in `vite.config.ts`:

```ts
import { defineConfig } from 'vite'
import { drawnAnnotationEditor } from 'slidev-theme-kotlin/annotation-editor'

export default defineConfig({
  plugins: [drawnAnnotationEditor()],
})
```

The plugin provides a development-only endpoint, for example:

```text
GET  /__drawn-annotations          -> current parsed geometry + revision
POST /__drawn-annotations          -> validated patch + expected revision
```

Server responsibilities:

- run only in Vite serve mode;
- use a fixed configured output path under the project root;
- accept geometry data, never an arbitrary client-supplied path or CSS text;
- validate IDs, finite numbers, ranges, and payload size;
- reject stale revisions with `409` rather than overwriting a newer edit;
- serialize deterministic CSS;
- write to a temporary file and atomically rename it;
- let Vite CSS HMR propagate the change;
- return clear errors to the toolbar.

Clamp label coordinates to a modest safe range by default (for example `0..1`) and connector coordinates to a configurable overscan range if authors need a stroke to begin slightly off-slide. Width must have a readable minimum and maximum.

If the plugin is absent, the editor toggle should either stay hidden or show a clear “annotation writer plugin is not configured” message. Never silently claim a save succeeded.

### Alternative if avoiding a Vite plugin is more important than CSS

Slidev's development server already supports slide patches and its built-in `v-drag` uses that facility to update slide frontmatter/content. We could persist annotation geometry in slide frontmatter through the same mechanism. That reduces setup but does not meet the project-CSS goal and couples geometry to Markdown slides, so it should be treated as a fallback, not the primary design.

## 9. Clicks, Magic Move, and state policy

Keep the existing lifecycle contracts:

- source marks continue to follow moving source content;
- label and manual connector geometry remain fixed in slide coordinates;
- automatic connectors continue following source/label until converted to manual mode;
- exit fades freeze geometry;
- hidden/preloaded slides cannot become editable;
- print/export reads persisted CSS synchronously and includes no editor controls.

For the first release, one annotation ID has one saved geometry across its visibility interval. If the same annotation genuinely needs different geometry at different click states, give those semantic instances different IDs.

A future extension can add an explicit state key and selectors such as:

```css
[data-drawn-annotation-id="example"][data-drawn-annotation-state="3"] { ... }
```

Do not implicitly key persistence by current click; doing so would create surprising duplicate layouts while the user navigates.

## 10. Accessibility and input

- Editor handles are development controls and must not appear in the accessibility tree outside edit mode.
- In edit mode, handles have labels such as “move annotation label” and “connector start”.
- Support arrow-key nudging; use a modifier for larger steps.
- Keep the existing live-region announcement for annotation labels unchanged.
- Pointer capture is required so a drag remains stable when the pointer leaves a small handle.
- Editing must prevent Slidev click navigation only while interacting with an editor control.

## 11. Testing strategy

### Unit tests

- CSS variable parsing and malformed-value fallback;
- normalization and viewport/slide/local coordinate conversion under non-uniform scale;
- deterministic CSS serialization and stable ordering;
- endpoint translation, resizing, clamping, and snapping;
- duplicate/missing ID diagnostics;
- revision conflict handling.

### Browser integration tests

- drag a label at two presentation scales and save identical normalized geometry;
- resize a label and verify wrapping after HMR and reload;
- drag connector endpoints and body, then reload and compare geometry;
- nested positioned/transformed component uses the slide origin correctly;
- current click and slide do not change while editing;
- Magic Move source tracking remains intact;
- backward navigation and exit fades remain intact;
- absent writer plugin cannot report success;
- print/export has saved geometry and no controls;
- cold reload produces the same screenshot and canonical geometry.

### Manual review

Use the existing annotation review manifest to manually place the currently bad cases. The old review regions become authoring guidance rather than an automated solver oracle. Review desktop, presenter view, iPad/Safari, and exact-click exports.

## 12. Delivery phases and gates

### Phase 0 — interaction spike

- Add explicit IDs to a few representative annotations.
- Prototype one label drag and connector endpoint drag with in-memory state only.
- Prove coordinate conversion on a normal slide, a scaled presenter view, and a nested component.

**Gate:** the same normalized geometry renders identically in all three contexts.

### Phase 1 — persisted label MVP

- Add the Vite writer plugin and deterministic generated CSS.
- Add CSS geometry parsing and precedence.
- Add toolbar, selection, label movement, width resize, reset, and save status.

**Gate:** drag, reload, build, and PNG export all agree.

### Phase 2 — connector editing

- Add endpoint and body handles.
- Preserve RoughJS style, stable seed, curve, arrow orientation, and animation.
- Add attached/manual toggle and basic snapping.

**Gate:** connector changes survive reload and remain visually stable under scale and export.

### Phase 3 — component simplification

- Replace broad obstacle scanning and future-state placement with simple defaults plus persisted overrides.
- Retain source measurement, target measurement, animation settling, and diagnostics.
- Remove solver-specific caches and warnings only after characterization tests protect retained behavior.

**Gate:** existing non-positioning behavior passes, and curated slides have authored geometry.

### Phase 4 — authoring polish

- Keyboard movement, undo, guides, better conflicts/errors, and documentation.
- Batch review all deck annotations and commit generated CSS.

**Gate:** authors can correct annotations without opening source files, and production/export contains no editor runtime.

## Implementation progress

- **Phase 0:** representative deck annotations have stable IDs, and renderer/editor coordinate conversion is covered for nested SVG canvases and presentation scale.
- **Phase 1:** the opt-in development Vite writer, deterministic generated stylesheet, revision protection, label drag/resize, reset controls, and CSS precedence are implemented.
- **Phase 2:** manual two-endpoint connectors support endpoint/body movement, attached/manual switching, RoughJS/arrow preservation, and source/target/label/slide snapping.
- **Phase 3:** runtime placement now uses bounded local defaults and persisted overrides instead of broad obstacle/future-state solving.
- **Phase 4 (current):** keyboard nudging, undo, conflict reload, visible guides, accessible focus targets (including the connector body), and click-outside selection clearing are implemented. Remaining work is browser-level interaction coverage and a full authoring pass over curated deck annotations.

## 13. Main risks and decisions to validate early

1. **Theme integration:** a theme cannot grant browser file-system access. The small consumer Vite-plugin setup is the principal cost of writing CSS rather than slide frontmatter.
2. **Stable IDs:** globally unique authored IDs are required for CSS that survives slide reordering.
3. **Coordinate ownership:** nested components make naïve CSS percentages incorrect; all persistence and controls must use the concrete slide root.
4. **CSS HMR feedback:** draft state and persisted state need revisions to prevent snap-back or stale overwrites.
5. **Manual connector semantics:** independent endpoints are flexible but can detach from moving Magic Move content. The attached/manual distinction must be visible and intentional.
6. **Responsive typography:** normalized position is scalable, but line wrapping can still change if fonts or canvas aspect ratio change. Persist normalized width and treat the configured Slidev canvas as the authoring contract.

## Recommendation

Proceed with the manual-first approach as a focused spike before investing in the automatic rewrite. It has a much smaller geometry problem, gives authors exact control, and turns the reviewed “bad” states into a finite authoring task. The spike should first prove the two hard boundaries—slide-root coordinate conversion and safe CSS persistence—because the rest is conventional Vue pointer interaction and existing DrawnAnnotation rendering behavior.
